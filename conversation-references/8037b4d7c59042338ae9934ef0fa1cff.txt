- 页面连续性与缓存（2026-10-21）：切页先销毁整页、再顺序获取空间详情及列表，会令每次点击都出现空白和重复加载。标题与导航应独立于内容区；同一登录会话内的已访问数据可先显示，再后台核对，表格按稳定记录 ID 更新并恢复选择、搜索和滚动。未变化的列表不重复读取成员和模型；轮询只在事件版本变化时更新内容。请求完成必须同时匹配请求标识、页面代次和客户端身份，旧请求不能清除新请求的 busy 状态；传输进度也必须携带身份与页面代次。切换账号或登录失效清空浏览缓存，明确 403/404/410 时移除相应受保护缓存，返回上页不能重新展示已知撤回的正文。草稿和本机文件不因此删除。
- 原生键盘交互（2026-10-21）：嵌入工作区的 `QDialog` 仍保留对话框默认按钮语义，搜索框按回车可能触发“团队空间”导航。页面按钮设置 `setAutoDefault(False)`，由搜索框处理回车；验收使用真实 `QTest.keyClick`，不能只直接调用搜索函数。验证：`.venv/Scripts/python.exe -X utf8 -m pytest -q test/test_team_space_ui.py test/test_team_space_client.py test/test_team_spaces.py`；缩放设置 `QT_SCALE_FACTOR=1.5`，截图和覆盖范围见 历史验证材料（已清理） 的统一交互记录。
- 首次绘制与表格高度（2026-10-21）：主题绑定只在主题管理器已就绪时立即执行，异步读取成功后才统一应用样式会留下未着色的占位条和原生输入框。新占位组件先应用当前主题，页面在发起读取前完成控件样式。无内部滚动条的表格须在 QSS 生效后重新排布并计算表头、行和边框高度；先算高度再加行内边距会裁掉末行。验证使用上述原生用例中的 `first_space_load`、`folder_navigation` 和 `theme_preview`，检查数据返回前截图及末行实际矩形，100%/150% 均验证。

- 空间归属不能仅保存在可被覆盖的会话 `meta`，也不能根据当前页面或工作目录推断。独立绑定记录与检测标记在同一 SQLite 事务保存；常规历史更新保留标记。绑定缺失、损坏或不兼容时，在现有 Worker 的终止错误通道结束，保留已提交消息；不要让构造上下文的异常直接逃出 Qt 槽而令界面停在运行中。旧普通会话不新增中心依赖，目录归档和普通侧栏分组跳过空间记录。
- SDK 内部重试不会再次经过外层 `chat_stream` 包装。空间调用关闭 SDK 隐式重试，在实际出站点核对中心策略，继续复用 Provider 原有可观察、有界重试；中心离线或撤权错误本身不得自动重试。即使使用 `raise ... from None`，异常仍可能有 `__context__`，通用网络错误分类必须先识别 `TeamSpaceError`。主循环、内部 Skill 模型调用、工具续轮均绑定原账号与登录代次。
- 发布成功但确认响应丢失时，重试必须先查询原操作。不能先重新上传已被发布事务消耗的附件，也不能将“暂未查到”解释为允许新建操作；冻结内容和原操作 ID 继续使用。已收到确定的业务拒绝才允许修改草稿后生成新提交。资料和成果的界面入口必须带固定修订，不能只打开对象的最新版本。

# LibreOffice 转换进程、Windows 长路径与 Linux 字体（2026-11-04）

- 现象：Windows 转换超时后子进程仍写文件；根因是先启动再绑定 Job 存在竞态，已生成的子进程不自动追溯加入 Job。文档执行器改为 CREATE_SUSPENDED → 绑定独立 Job → ResumeThread；Unix 从启动时创建独立会话，按自己保存的 PID 清理进程组。Job 关闭触发的是异步终止，不能只等待 soffice.com 退出；清理配置前记录 Job 成员的进程句柄，显式 TerminateJobObject 并有界等待这些句柄结束；单看 Job 活动计数归零仍可能早于内存映射文件释放，不能用它代替进程句柄等待。不要按 soffice 进程名清理用户实例。
- 现象：PDF 已生成，但清理扩展缓存时报 WinError 145。LibreOffice 的用户配置会生成超过 MAX_PATH 的深层目录。CLI 和 UserInstallation 保持普通路径/文件 URI，仅删除自有临时目录时使用 Windows 扩展路径；不要忽略清理异常伪造成功。
- MSI 管理解包不会替用户安装 VC 运行库或注册字体；将原包 System64 的 DLL 复制到 program，将 Fonts 复制到 share/fonts/truetype，保持进程私有字体和随包许可证。真实解包目录转换通过不等于干净机器安装包通过。
- Ubuntu 最小镜像中的 QtGui/QtPdf 还需要 libGL.so.1/libatomic.so.1；只装 LibreOffice 并不足以生成 PPT PNG。缺少 Calibri 兼容字体时 fc-match 会落到等宽字体，PDF 文本仍可提取但间距明显变化；镜像补齐 Carlito/Caladea，并用逐页截图核对。QPdfDocument.render 的透明背景在截图时要合成白底，避免误判黑字丢失。
- 验证：启用 COWORK_TEST_LIBREOFFICE=1 后运行 `.venv/Scripts/python.exe -X utf8 -B -m pytest test/test_libreoffice.py test/test_presentation_renderer.py -q -p no:cacheprovider`；Docker 命令见 `test/docker/libreoffice/README.md`。运行 `scripts/smoke_office_preview.py --output .tmp/cross-platform-research/smoke-windows` 检查双页文档、双工作表和 PPT 的源哈希、页数、公式与逐页 PNG。Windows bind mount 的 Unix 临时文件权限不能替代原生目录语义；进程契约测试使用任务路径上的 tmpfs。
- 预防：固定组件来源与摘要；缓存区分引擎版本、字体和配置。PDF 退出码、页数、文字提取和截图是不同证据，不能用其中一项代表所有版式都通过；Windows/Ubuntu 版本不同或未做 macOS 实测时明确记录边界。

## Electron 宿主、冻结服务与插件页面（2026-11-08）

- 终端能显示提示符但输入卡住，不一定是 React 焦点问题：ConPTY 会等待 xterm 的 DA/DSR 应答。桥接迁移必须保留协议回复白名单，即使用户输入被锁定也允许协议应答；不能只转发 input/resize。端到端测试必须同时验证命令和独立执行回显，不能以输出包含用户输入作为命令执行证据。验证：`python -X utf8 -B -m pytest -q -p no:cacheprovider test/test_desktop_workbench.py`，以及实际界面输入、切页再返回。

- Windows / Python 3.14 的桌面 RPC 首次打开 XLSX 超时，但同文件在主线程直接打开正常。`faulthandler` 显示 RPC 线程停在 `openpyxl → numpy._core.multiarray` 的扩展模块初始化。桌面服务在创建工作线程之前预加载 `openpyxl` 后，真实服务中的表格读取、修改保存与外部修改冲突回归通过。预防：需要原生扩展的共享文档依赖在服务启动边界初始化；不要加长 RPC 超时或跳过冲突检查。验证：`python -X utf8 -B -m pytest -q -p no:cacheprovider test/test_desktop_management.py`；设置 `COWORK_TEST_TRACE_TIMEOUT=1` 可让集成夹具在 12 秒时输出线程堆栈，日志仍写入隔离目录。
- `web/editors/node_modules` 来自其他操作系统时，目录存在不代表可构建；本机曾只有 `@esbuild/linux-x64`。按锁文件安装匹配平台的包并校验 integrity，再运行 `node web/editors/build.mjs`。构建脚本会先清理 `dist`，失败后必须修复并重建，不能沿用缺失的静态资源。Electron 打包也必须先构建编辑器并拷贝完整 `dist`。
- JSONL 服务等待首个模型请求时卡住，堆栈可能实际停在 `bash --version` 运行时探测。被探测进程继承协议 stdin 后会占用宿主输入；探测统一使用 `subprocess.DEVNULL`，包括 Node/Python 组件状态探测，并设置有界超时；标准输出仍只承载协议，诊断输出转到 stderr。不要通过另起执行路径绕过原 Worker。
- 源码以 `-X utf8` 启动通过，不代表 PyInstaller 成品使用相同编码。中文 Windows 冻结服务实测输出系统代码页，宿主的 UTF‑8 JSONL 解码失败；服务入口对 stdin/stdout/stderr 显式 `reconfigure(encoding="utf-8")`。同一集成用例须通过 `COWORK_TEST_DESKTOP_SERVICE` 运行随包 EXE，并把 cwd 设为隔离目录，覆盖中文消息、即时停止、补充、强制退出恢复和保存冲突。命令见 `docs/technical-design.md` 的 Electron 工作台章节。
- `srcdoc` 页面继承父页 CSP，父页禁止 inline script 时，插件自己的宽松 meta 不能使脚本执行。使用仅提供已批准内容快照的独立 `cowork-plugin:` 协议，保留 iframe sandbox 与插件自身禁止网络的 CSP；不要放宽主界面脚本策略。实际验证编辑、Ctrl+S 和 GFM 表格预览，不能只看 iframe 有内容就认为接口接通。
- Electron Packager 18 的钩子使用回调契约，直接传 async 函数会留下未完成 Promise，Node 报 unsettled top-level await。使用包自带 `serialHooks` 适配异步步骤；必须检查最终 `Cowork.exe` 及随包服务，不能把 PyInstaller 完成当作整包成功。
- Windows 界面回归的临时路径也会进入运行记录的多层哈希目录；仓库内测试根使用较短的 `.tmp/q` 等路径。长路径失败要检查真实路径和原始异常，不通过取消断言或忽略清理失败使测试通过。
- 原生目录选择框的自动化可访问焦点可能滞后，甚至将文件夹输入框误报为搜索框；同时弹窗元素索引可能不可操作。不要反复重试旧索引：用新截图确认插入光标，输入后核对文件夹字段的实际值。输入完整目录后第一次 Enter 可能只进入目录，需确认地址栏已定位，再按 Enter 完成选择；以插件预览实际出现作为成功依据。本次验证完整覆盖预览编辑、应用、返回文稿和恢复内置版本。

- Electron 的 Windows 后台服务使用 `detached:true` 会创建独立控制台，`windowsHide:true` 不能可靠抵消。独立服务寿命通过 stdio 释放与 `unref()` 保持，Windows 不使用 detached；GUI 启动用 CREATE_NO_WINDOW，不设置 SW_HIDE 隐藏主窗口。验证：实际启动无额外 PowerShell 窗口，退出界面后重连同一服务；`desktop/tests/backend.test.mjs`。

## 文档升版与跨进程验证边界（2026-11-14）

- 现象：全量测试启动后更新 APP_VERSION 与版本文档，已导入旧常量的测试进程读取到新文档，产生版本不一致和尚未落盘的发布说明缺失。根因是验证期间修改了被验证快照。方法：完成该批编辑再运行版本与文档检查；该轮混合快照结果只能用于诊断，不能当作最终验收。验证：`.venv/Scripts/python.exe -X utf8 -B scripts/check_docs.py` 与 `test/test_documentation.py`。
- 新增版本说明尚未暂存时，文档检查只用 `git ls-files` 会把正式新文件误判为本地私有文件。检查候选改为 `git ls-files --cached --others --exclude-standard`；新文档可在暂存前验证，忽略的手记仍不可作为正式文档依赖。验证上述文档检查，并用 `git check-ignore -v` 与 `git ls-files` 核对本地手记。
- 父解释器 `-X utf8` 不自动传给 Python 子进程，Wind 本地脚本在 Windows GBK 控制台输出 emoji 时失败。测试进程设置 `PYTHONUTF8=1` 后对应本地夹具通过；开发命令同步声明该变量。复核入口：`test/test_wind_aifinmarket_skill.py`。
- 随包 node_env 可能是精简执行运行时，目录中能运行 node.exe 不代表 npm CLI 依赖完整。本次 npm 报缺少 npm-prefix.js；依赖已安装时直接调用 package.json 对应的 Node 测试／构建入口，安装依赖仍使用带 npm 的开发环境。不要因此重复安装全部前端包或误判应用测试失败。
- 退役脚本不能只删除被调用文件：Qt smoke 已删除，但 Python 测试和 benchmark 仍通过子进程路径启动它们，导致“文件不存在”。清理时同时搜索脚本名、CLI 选项和 Qt 环境变量，保留宿主无关业务检查及“禁止 Qt 进入服务／发行包”的负向断言。Electron 默认配置测试必须使用 `resources/service/_internal/config.json` 和当前发行夹具，不能为复用旧测试再混入 Qt DLL。验证：`.venv/Scripts/python.exe -X utf8 -B -m pytest -q -p no:cacheprovider test/test_deliverable_editor_web.py test/test_package_default_config.py test/test_package_release.py test/test_packaging_runtime.py`；用户明确暂缓的集成用例需在现行文档标明覆盖范围和未修复状态，不能计作通过。

方法论\r\n\r\n**依赖是否安装成功，必须在最终执行环境中验证，而不是在安装环境中验证。**\r\n\r\n对桌面应用而言，源码测试、打包目录测试和干净用户环境测试是三个不同层级。运行时路径、动态库和外部进程都应集中解析，不能让每个工具自行猜测环境。\r\n\r\n## 五、异步化解决卡顿，也可能制造更隐蔽的竞态\r\n\r\n### 踩坑现象\r\n\r\n为了让 UI 历史还未加载完成，保存队列先写入空会话；\r\n- 高频流式 token 触发大量 Qt 富文本重排；\r\n- 文件监听事件风暴导致 HTML 反复刷新。\r\n\r\n### 根因\r\n\r\n异步化降低了单次等待时间，却增加了状态数量和时序组合。原本同步代码中的隐含顺序消失后，如果没有显式生命周期和幂等设计，系统就会在边界条件下出现竞态。\r\n\r\n### 解决方式\r\n\r\n我的处理方式不是继续增加更多线程，而是减少共享状态：\r\n\r\n- 将子 Agent 的结果持久化、状态流转和线程回收拆分；\r\n- daemon 启动请求合并，并使用进程锁保证单实例；\r\n- 保存队列按会话合并和防抖，强一致操作显式等待；\r\n- 流式输出按短时间窗合并刷新，而不是每个 token 重排 UI；\r\n- 子 Agent 事件先写入队列，打开面板后再由主线程分批渲染；\r\n- 文件扫描和监听事件防抖，内容指纹未变化时复用现有页面。\r\n\r\n### 方法论\r\n\r\n**异步系统优化的重点不是“把事情放到后台”，而是定义生命周期、幂等性和状态归属。**\r\n\r\n先减少共享可变状态，再增加并发；先让任务可以安全地重复触发，再追求更快响应。性能优化必须与一致性设计同时进行。\r\n\r\n## 六、子 Agent 的难点不在创建，而在收敛与回收\r\n\r\n### 踩坑现象\r\n\r\n子 Agent 最初很容易实现出“能够启动”的版本，但真实使用很快暴露出更多问题：状态长时间停留在 running 或 waiting、结果无法稳定返回主 Agent、继续输入后上下文丢失、多个子任务完成时 UI 崩溃、后台线程退出顺序不确定。\r\n\r\n### 根因\r\n\r\n子 Agent 同时具有工具和独立执行主体的双重特征。主 Agent 需要把它当作一次可等待的调用，UI 又需要把它当作有持续状态的任务。如果结果、状态、事件和线程生命周期绑定在一起，任何一个环节出错都会影响其他环节。\r\n\r\n### 解决方式\r\n\r\n我把子 Agent 拆成四个彼此关联但独立的层次：\r\n\r\n1. 任务身份与父子关系；\r\n2. 输入、工具和输出事件流；\r\n3. 可持久化的结果与终止状态；\r\n4. worker 与线程资源回收。\r\n\r\n最终结果先持久化，终止状态再确认，线程回收最后进行。UI 只消费状态事件和轻量摘要，不直接控制 worker 生命周期。高频诊断日志默认关闭，需要排查时再开启，真正的异常始终保留完整 traceback。\r\n\r\n### 方法论\r\n\r\n**多智能体首先是任务生命周期问题，其次才是模型协作问题。**\r\n\r\n设计子 Agent 时，应先定义状态机、终止条件、结果所有权、超时与回收顺序，再讨论角色分工和 Prompt。无法可靠结束的 Agent，不具备可靠协作的基础。\r\n\r\n## 七、UI 卡顿往往不是“Qt 性能差”，而是渲染策略错误\r\n\r\n### 踩坑现象\r\n\r\n长对话、流式输出和复杂工具卡片曾导致界面闪烁、滚动卡顿、气泡高度异常，甚至在历史面板打开时明显阻塞。最直接的修补方式是减少内容或关闭富文本，但这会牺牲交付质量。\r\n\r\n### 根因\r\n\r\n问题通常不是内容本身太多，而是每次微小变化都触发完整布局和渲染：每个 token 重新生成 Markdown HTML，每次窗口变化重算所有气泡，每次打开侧栏创建大量复杂控件，远离视口的历史消息也持续占用布局成本。\r\n\r\n### 解决方式\r\n\r\n项目逐渐加入：\r\n\r\n- 流式片段合并刷新；\r\n- Markdown 与 HTML 渲染缓存；\r\n- 长回复的流式纯文本快路径；\r\n- 远离视口气泡的轻量占位；\r\n- 子 Agent 历史的延迟批量渲染；\r\n- 窗口和抽屉变化后的集中宽度重算；\r\n- 避免在高频事件中同步扫描磁盘或重建复杂 widget。\r\n\r\n### 方法论\r\n\r\n**UI 性能问题要沿“事件频率—计算范围—渲染成本”三层定位。**\r\n\r\n先判断是否触发得太频繁，再判断是否计算了过大的范围，最后才考虑单个控件是否昂贵。很多性能问题通过合并、缓存、虚拟化和延迟构造即可解决，不必牺牲内容完整性。\r\n\r\n## 八、HTML 能显示，不等于交付物体验成立\r\n\r\n### 踩坑现象\r\n\r\n交付物功能最初能够打开 HTML，但真实使用中出现了横向无法滚动、嵌套区域抢占滚轮、滚动条与滚轮行为不一致、切换会话后丢失当前产物、页面动画造成预览卡顿等问题。\r\n\r\n这些问题单独看都像小缺陷，叠加后却会让“生成—预览—修改—转换”整条链路无法使用。\r\n\r\n### 根因\r\n\r\n浏览器内容嵌入 Qt 后，输入事件横跨 Qt、QtWebEngine 和页面 JavaScript 三层。只在其中一层修复，会造成另一种交互路径失效。更根本的问题是，早期把 HTML 当作最终输出，而不是持续创作的源文件。\r\n\r\n### 解决方式\r\n\r\n我重新定义了交付物模型：HTML 是可持续修改的创作源，PPTX、DOCX 和 PDF 是从源文件派生的交付格式。右侧抽屉保留当前产物和布局状态，文件未变化时复用页面；滚轮与外置滚动条共享同一滚动路径，嵌套区域仍由页面内部处理；创建阶段限制高频动画和自动播放；格式转换在同一项目中继续对话并自动附加当前 HTML。\r\n\r\n### 方法论\r\n\r\n**不要按文件格式设计功能，要按用户完成工作的连续链路设计功能。**\r\n\r\n一个预览器是否成功，不取决于文件能否打开，而取决于用户能否围绕它持续阅读、修改、比较和交付。\r\n\r\n## 九、Apple 风格不是增加圆角，而是删除系统噪声\r\n\r\n### 踩坑现象\r\n\r\n功能增长后，设置、能力中心和自动化页面越来越像管理后台：大量边框、卡片、摘要数字和技术说明抢占注意力。即使换成浅色、圆角和蓝色按钮，界面仍然“太程序员化”。\r\n\r\n一次截图反馈非常直接：“都带着边框，太丑了。”进一步检查发现，问题不只来自主动添加的卡片，还来自 Qt 样式选择器向内部子控件泄漏，导致几乎每层容器都出现边框。\r\n\r\n### 根因\r\n\r\n我一度把视觉层级等同于容器层级：每一组内容都用卡片包裹，每一级结构都加边框。结果系统内部架构被原样映射到界面，用户必须先理解产品结构，才能找到操作。\r\n\r\n### 解决方式\r\n\r\n后续设计改为用间距、标题、对齐和背景层次组织内容，装饰性容器尽量无边框，只在输入、列表和可点击元素上保留操作暗示。右侧上下文默认隐藏，子 Agent 活动只点亮提示；设置页按用户决策而不是内部模块组织；共享 DesignTokens 和样式 helper，并将选择器约束到准确的 Qt 类型，避免继承泄漏。\r\n\r\n### 方法论\r\n\r\n**UI 的职责不是展示系统有多复杂，而是让用户不必理解复杂度。**\r\n\r\n所谓克制，不是少做功能，而是减少完成当前决策不需要的信息。视觉优化应优先做减法：删除边框、摘要、术语和重复说明，再考虑增加装饰。\r\n\r\n## 十、经验系统最危险的坑：把所有历史都当成知识\r\n\r\n### 踩坑现象\r\n\r\n智能体具备长期记忆后，很容易产生一种冲动：保存更多对话、自动提炼更多经验、每次任务都向系统提示词注入更多历史。结果是上下文越来越长，过期事实和错误尝试被反复召回，用户偶然说过的一句话也可能被错误固化。\r\n\r\n### 根因\r\n\r\n原始历史、用户记忆、执行经验和专业 Skill 的信息性质不同。把它们放入同一个“记忆库”，等于忽略了证据强度、适用范围和生命周期。\r\n\r\n### 解决方式\r\n\r\n我把这几类信息分层：\r\n\r\n- 会话历史保留发生过什么；\r\n- 长期记忆保存稳定事实与偏好；\r\n- 经验条目记录任务反馈与可复用教训；\r\n- Skill 组织专业方法、工具和已验证经验。\r\n\r\n经验条目保留来源、版本、重要度、使用次数与成功次数，并支持更新和回滚。“更新长期记忆”和“沉淀为 Skill”保留人工审阅，避免系统在没有证据的情况下自行强化结论。\r\n\r\n### 方法论\r\n\r\n**经验系统的目标不是最大化记忆量，而是提高未来决策的命中率。**\r\n\r\n任何准备长期保留的信息，都应回答：它来自哪里、在哪些任务中适用、是否经过验证、何时可能过期、出错后能否撤回。\r\n\r\n## 十一、最大的产品坑：不断增加能力，却没有定义边界\r\n\r\n### 踩坑现象\r\n\r\n通用智能体天然容易扩张：既然能写代码，也可以做 IDE；既然能分析数据，也可以做完整 BI；既然支持策略回测，也可以继续做量化平台。沿着每个方向深入，最终会得到多个互相竞争的半成品。\r\n\r\n### 根因\r\n\r\n“通用”很容易被误解为“什么都由本体实现”。这会让 Agent 内核、专业能力和产品界面不断耦合。\r\n\r\n### 解决方式\r\n\r\n我最终把边界定义为：通用的是任务闭环，专业的是 Skill。Cowork 本体提供工作区、上下文、工具发现、执行控制、观测、记忆和交付体验；AI 问数、量化、文档和行业能力以 Skill 接入。\r\n\r\n编程同样不是 Cowork 的主要竞争方向。代码阅读、实现和工程修改可以交给 Codex 等专业编程智能体，Cowork 更聚焦本地文件、数据、文档、浏览器、自动化和通用办公。专业智能体也可以成为整个工作体系中的一种工具，而不必被重新实现。\r\n\r\n### 方法论\r\n\r\n**平台的核心不是自己完成所有任务，而是让新能力以低成本、低耦合方式进入统一闭环。**\r\n\r\n判断一项功能应进入本体还是成为 Skill，可以问三个问题：它是否属于所有任务都需要的基础设施？它是否改变通用执行闭环？它能否独立演进和替换？只有前两个问题为“是”时，才更适合进入内核。\r\n\r\n### 追加案例：启动期重复扫描 Skill - 工具在开发环境正常，打包后找不到运行时。
- 生成了 HTML，但用户无法顺畅预览、修改和导出。
- 子 Agent 返回结果，主界面却一直显示任务运行中。

因此，文档把任务完成定义为一个完整闭环：

**理解目标 → 获取真实环境 → 选择能力 → 执行动作 → 验证变化 → 交付可继续使用的结果。**

其中最值得记住的一句话是：

> 不要验证模型是否说对了，要验证外部世界是否真的改变了。

从第一性原理看，这也是全文的出发点：用户需要的是任务结果，模型输出只是实现结果的一个环节。

**2. 工具、Skill、上下文和记忆，需要明确分工**

文档对智能体架构的一个重要判断是：能力不断增加时，必须控制复杂度。

| 组成部分 | 文档赋予它的主要职责 |
|---|---|
| Agent | 理解目标、编排任务、协调执行 |
| 工具 | 提供确定的执行接口 |
| Skill | 说明专业任务如何做、如何组合工具、如何验证 |
| 会话历史 | 记录发生过什么 |
| 长期记忆 | 保存稳定事实与偏好 |
| 经验 | 保存经过验证、可以复用的教训 |
| UI | 让用户了解状态、控制执行和接管任务 |

这里有两个很实用的结论。

一是，**工具越多，不一定越好用**。把全部工具和说明同时塞给模型，会增加选择混乱、上下文开销和缓存失效。因此应按任务逐步披露能力。

二是，**历史不应自动变成知识**。一次失败尝试、临时事实、偶然偏好，都不适合直接固化为长期记忆或 Skill。可复用经验应有来源、适用条件、验证依据，并能更新或撤回。

**3. 大量“AI 不稳定”，实际来自软件状态不一致**

这是全文技术含量较高、也很有普遍价值的部分。

一个会话可能同时存在于界面、后台线程、后台服务、保存队列和 SQLite 数据库中。如果这些位置保存的状态不同，就会出现：

- 界面有历史，后台却拿到空上下文。
- 用户编辑了消息，模型仍收到旧内容。
- 历史尚未加载完成，自动保存先把空会话写入数据库。
- 工具调用和工具结果不配对，模型接口报错。

文档因此提出：

> 上下文管理本质上是分布式状态一致性问题，即使系统只运行在一台电脑上。

对应的做法是明确：**谁保存权威状态、何时允许复制、何时必须同步、冲突时以谁为准。**

这条思路同样贯穿异步保存、模型设置草稿、侧栏搜索、任务状态和退出流程。

**4. 异步和多 Agent 的难点，在于可靠结束**

文档记录了不少线程、后台任务和子 Agent 的问题：任务已完成但状态没更新、旧回调清掉新线程引用、窗口销毁后后台仍访问控件、退出时结果尚未保存等。

它强调，增加并发之前，要先定义：

- 任务身份和状态归属。
- 完成、失败、取消的判定条件。
- 结果保存与状态更新的顺序。
- 超时后的处理方式。
- 线程和进程的回收边界。

例如，子 Agent 的收尾顺序被明确为：**先持久化最终结果，再确认终止状态，最后回收线程资源。**

另一个重要区分是：**工具把控制权交回，不代表执行结束；请求取消，不代表任务已经停止。** 这些状态必须分别表达并核验。

**5. “开发机上能跑”只是第一层验证**

文档包含大量 Windows、PyInstaller、Python、Node.js、Git Bash、QtWebEngine，以及 POSIX 终端相关经验。

它反复说明：源码环境、打包环境、用户机器是不同的执行环境。常见问题包括：

- 安装依赖用的 Python，与执行工具用的 Python 不同。
- 开发机有全局依赖，干净用户环境没有。
- 打包后资源路径、DLL 搜索路径发生变化。
- 更新完成后仍引用旧运行时。
- Shell 退出了，后台子进程却没有退出。

所以它要求：**依赖和功能应在最终执行环境中验证。** 安装命令成功、子进程退出码为零、安装器完成，都不能单独证明用户所需功能已经可用。

**6. 性能和界面问题，要沿真实使用链路定位**

文档对 UI 的讨论很具体，涉及长对话、流式输出、滚动、主题、缩放、编辑状态和交付物预览。

性能方面，它给出一个清晰的排查顺序：

**事件是否太频繁 → 每次计算范围是否太大 → 单次渲染是否太贵。**

例如，每个 token 都重排全文、每次输入都扫描所有消息、每次打开面板都创建大量控件，都可能造成卡顿。相应手段包括合并刷新、缓存、分页、延迟构造和只渲染必要内容。

产品方面，它强调：界面应围绕用户完成工作的连续过程设计。例如，HTML 交付物需要支持阅读、修改、预览和转换；“文件能打开”只是其中一步。界面也应减少无关边框、术语和状态，让用户容易找到当前需要的操作。
