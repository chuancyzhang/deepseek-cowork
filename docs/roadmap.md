## 当前阶段

**阶段：5.1.0 发布与稳定观察**

这一阶段的目标是形成可发布、可诊断、可复现的统一基线。优先级从高到低为：

1. **P0 · 发布闭环**：版本、发行标签、发布说明、依赖、离线资源、更新器和打包审计一致。
2. **P0 · 核心可靠性**：模型协议、Tool 暴露、文件读写、历史恢复和后台进程遇到错误时明确失败。
3. **P1 · 用户任务路径**：能力启用、文件编辑、企业消息和首页入口保持简单，并覆盖空、加载、成功、失败与恢复状态。
4. **P1 · 诊断可复用**：关键提交、启动、运行、完成和错误路径有结构化日志与可重复验证命令。

## 当前基线

当前版本已经具备三条完整主链：

- **执行链**：模型 → Agent Loop → Tool Registry → 内置/Skill/MCP Tool → 观测与持久化。
- **交付链**：工作区/附件 → 生成 → 预览 → 兼容预检 → 安全编辑 → Office/PDF 转换。
- **扩展链**：能力商城/Agent/自动化 → 配置与按需依赖 → 热更新 → 后台或企业消息运行。

主题、记忆和经验横跨三条主链，但不改变它们的权限与保存边界。

## 近期重点

### 运行可靠性

- 持续覆盖 DeepSeek Responses 与其他 Provider 在多轮 reasoning、Tool 和服务端能力上的协议差异。
- 完善多 Agent、自动化、daemon 和企业消息的结束状态、重试边界与诊断对账。
- 为普通文本补丁、交付物保存、历史恢复和应用更新增加更集中的发布验收。

### 产品体验

- 继续减少能力设置、组件准备和高级管理之间的概念跳转。
- 统一长任务、等待确认、后台完成、冲突和失败恢复的状态文案。
- 保持主内容优先，在窄窗口和 Windows 缩放下验证导航、编辑器与关键操作。

### 工程维护

- 继续从 `main.py` 拆分已经稳定且边界清晰的 UI 子系统。
- 收敛重复的注册表、状态机和持久化过滤规则，避免 UI、daemon 与打包态行为分叉。
- 保持可选运行时延迟准备，控制发行体积和启动导入路径。

## 候选方向

以下内容仍是候选，不构成发布承诺：

- 更清晰的 Agent 任务分解、委派策略和跨 Agent 结果汇总；
- 更系统的经验检索、去重、质量评分和人工整理；
- MCP Resource 与 Prompt 的完整运行时接入；
- 更轻量的文档、数据和浏览器运行组件；
- 在安全声明边界内扩展 AI 设计 UI 的布局与内容能力；
- 面向长期任务的资源预算、断点恢复和跨设备可观测性。

## 维护规则

- 当前版本以 `core/app_version.py` 为唯一来源，GitHub Release 标签必须与其一致。
- 路线图不保存提交流水账，也不复制发布说明。
- 只有已进入源码和测试的能力才能写入“当前基线”。
- 候选方向必须标明不确定性，不用计划措辞暗示已经承诺。
