# 后续 UI 性能优化准则

本文用于指导后续 Cowork UI 性能设计、实现和验收。它建立在[对话第一性原则](CONVERSATION_FIRST_PRINCIPLES.md)和[对话可靠性与呈现设计原则](CONVERSATION_RELIABILITY_AND_PRESENTATION_PRINCIPLES.md)之上。

## 核心命题

完整维护对话事实，按用户需要生成界面；让每次变化只触发必要、局部、可控的工作。

这里的“事实”包括用户已经发送的内容、AI 已经展示的正文、真实的工具调用与结果、用户引导及明确的停止、失败和编辑结果。界面是这些事实的投影，不是事实的唯一存储位置。

## 设计原则

### 1. 完整维护对话事实，按用户需要生成界面

SQLite 中的已提交聊天历史是唯一的聊天事实来源；运行日志保存运行过程；UI 保存展示投影。折叠、分页、虚拟化、延迟渲染和摘要只能改变内容创建或显示的时机，不能删除事实、改变顺序或伪造回答。

### 2. 界面负责表达状态，控件是否存在不决定事实是否存在

控件可以隐藏、延迟创建或暂时卸载，但会话状态、运行身份、消息内容和保存进度必须继续由对应的 `SessionState` 或持久化层持有。后台会话切回时，应从最新状态恢复投影；运行完成、内容已保存和界面已绘制是三个不同状态，不能互相替代。

### 3. 增量更新要贯穿数据、文本、布局和控件

一次追加应尽量只处理新增片段及其影响的末尾区域：

- 数据层追加事件或版本化快照，避免用完整列表覆盖；
- 文本层追加稳定后缀，避免反复拼接、扫描和解析全文；
- 布局层合并同一轮的几何更新，避免每个字符触发父级重排；
- 控件层只创建、更新或销毁真正变化的对象，保留未变化对象和用户选区、滚动位置。

如果变化确实影响宽度、字体、主题或内容语义，才重新计算受影响的范围，并记录原因。

### 4. 根据数据性质决定合并策略

合并必须以语义等价为前提，而不是只看性能收益：

| 数据 | 处理方式 |
| --- | --- |
| 同一运行中相邻的文本增量 | 按原顺序拼接，保留全部字符 |
| 同一对象的周期性完整快照 | 在身份和版本有效时合并较新的待处理快照 |
| 工具调用、工具结果、用户引导、阶段切换、停止、失败、完成 | 作为语义边界保序，不能吞并或重排 |
| 未变化的状态通知和重复布局请求 | 去重或合并，避免重复进入 UI 线程 |

事件合并必须保留 `session_id + turn_id + request_id/run_id` 等身份；旧事件、迟到事件和其他会话事件不得进入当前投影。

### 5. 按用户当前需要分配计算资源，同时保留完整访问能力

输入反馈、停止操作、当前阅读区域、运行状态和错误恢复优先获得主线程预算。隐藏会话、折叠思考过程、未展开详情和不可见产物可以延迟渲染，但用户展开或切回时仍应能够访问完整内容。

延迟渲染需要配套恢复策略：分批创建、稳定滚动、可见进度和可理解的失败反馈，避免把一次持续的小成本转移成切回时的大停顿。


## 工程规则

性能优化可以改变计算方式、批次、调度、缓存和展示投影；必须保持对话事实、因果顺序、持久化承诺、会话身份与用户控制权不变。

实施时应遵守以下约束：

1. 先区分聊天事实、运行事实和展示事实，再决定是否缓存、合并、延迟或丢弃。
2. 高频生产必须在进入 Qt UI 线程前形成背压；队列、批次、字节数和单批工作时间应有界，并记录积压和失败指标。
3. 相邻文本可以合并，语义边界必须立即或按明确屏障处理；停止、关闭、重连和切换运行时要封存或丢弃旧 buffer。
4. 持久化应减少写放大而不是减少事实：高频事件采用有序追加，低频状态采用版本化快照；发布给 UI 前先确认数据已可靠落盘。
5. 隐藏或延迟的 UI 不能成为运行完成、消息保存或历史加载的前置条件；历史加载只能读取和投影，不能反向补写历史。
6. 用户已经看到的非空正文、已经发送的消息和已经发生的引导必须可恢复；失败应保留成果并提供重试或继续路径。
7. 任何异步回调都必须验证会话、轮次和运行身份；旧状态不能覆盖新事实。
8. 不把 UI 折叠状态、重试提示、诊断信息或普通错误写入模型聊天历史，避免污染协议和 prompt 前缀。

## 评审时的五个问题

1. 这次优化减少的是重复计算，还是误删了事实或跳过了必要步骤？
2. 用户已经发送或看见的内容，在停止、失败、切换和重启后是否仍然存在？
3. 合并、延迟和虚拟化是否保持了真实顺序、工具配对、会话隔离和用户控制？
4. 主线程是否仍能及时响应输入、滚动、停止和恢复？积压、单次最长耗时和失败是否可观测？
5. 用户完成真实任务的总成本是否下降，而不是只让某个局部指标变好？

只要这些问题没有得到肯定回答，就不能把一次局部的刷新变快视为 UI 性能优化完成。
